## 과제 개요

- 이 과제에서는 동시 요청이 몰려도 결과가 틀리지 않는 코드를 작성하고, 그렇게 구현한 이유를 설명할 수 있는지를 봅니다.
- 시작 프로젝트의 결제 컨트롤러를 완성하고, 기존 수수료 코드를 리팩토링합니다.
  - 기술 스택은 Java 17, Spring Boot 4.1.1, Gradle이며 DB는 사용하지 않습니다.
- `TODO`가 표시된 시작 프로젝트, 수정할 수 없는 한도 저장소, 서술 템플릿을 제공합니다.
- 제한 시간은 없습니다.
- 한도 저장소는 호출할 때마다 일부러 지연이 생기도록 만들었습니다. 한도를 확인하고 차감하는 사이에 다른 요청이 끼어들 수 있으니 주의해 주세요.

## 1. 과제 소개

카드 결제 서버를 완성하는 과제입니다.

- 사용자마다 1,000,000원의 한도가 있습니다.
- 결제를 승인하면 한도가 줄어들고, 취소하면 다시 돌아옵니다.
- 결제마다 수수료를 계산합니다.

요청이 동시에 몰릴 때도 다음과 같은 일이 생기면 안 됩니다.

- 같은 결제가 두 번 승인됨
- 동시에 들어온 결제 때문에 한도를 넘어 승인됨
- 기록된 사용액이 실제 승인 금액과 달라짐

> [!TIP]
> 이 과제에서 확인하는 것은 다음 네 가지입니다.
> - 동시 요청에서도 결과가 틀리지 않는가
> - 수수료 규칙을 경계값까지 표대로 구현했는가
> - 구현이 맞다는 것을 테스트로 보여 주는가
> - 그렇게 구현한 이유를 글로 설명할 수 있는가

1. `starter-project/`를 IntelliJ에서 엽니다.
2. 서버를 실행합니다. 서버는 `8080` 포트에서 실행됩니다.

## 4. 용어 설명

| 용어 | 뜻 |
|---|---|
| **동시성 문제 (경합)** | 여러 요청이 같은 데이터를 동시에 수정할 때 결과가 어긋나는 문제 |
| **확인 후 실행 (check-then-act)** | 한도가 남았는지 확인한 뒤 차감하는 것처럼, 확인과 실행 사이에 다른 요청이 끼어들 수 있는 코드 패턴 |
| **락 (잠금)** | 특정 구간을 한 번에 한 요청만 실행하도록 막는 장치. 어떤 범위를 잠그는지에 따라 결과와 성능이 달라집니다. |
| **불변 조건** | 언제나 참이어야 하는 규칙. 이 과제에서는 `사용액 = 취소되지 않은 승인 결제 금액의 합`입니다. |
| **경계값** | 규칙이 바뀌는 값과 그 앞뒤 값 (예: 999원과 1,000원) |
| **절사** | 소수점 아래를 버리는 것. 반올림과 결과가 다릅니다. |
| **리팩토링** | 동작은 그대로 두고 코드를 읽기 쉽게 정리하는 것 |

## 5. API 명세

### 5-1. 결제 승인

`POST /api/v1/payments`

```json
{ "paymentId": "P-1001", "userId": "U-1", "amount": 50000, "grade": "GOLD", "payType": "DOMESTIC" }
```

| 필드 | 규칙 |
|---|---|
| `paymentId` | 결제 ID. 필수, 1~50자. 모든 사용자를 통틀어 유일해야 합니다. |
| `userId` | 사용자 ID. 필수, 1~50자 |
| `amount` | 결제 금액(원). 정수, 1 이상 100,000,000 이하 |
| `grade` | `BASIC`, `SILVER`, `GOLD`, `VIP` 중 하나 |
| `payType` | `DOMESTIC`(국내), `OVERSEAS`(해외) 중 하나 |

**응답**

| 상황 | 상태 코드 | 본문 |
|---|---|---|
| 승인 | **200** | `{"paymentId":"P-1001","userId":"U-1","amount":50000,"fee":250,"status":"APPROVED","remainingLimit":950000}` |
| 입력 오류 | **400** | 에러 본문 (`INVALID_REQUEST`) |
| 이미 있는 결제 ID | **409** | 에러 본문 (`DUPLICATE_PAYMENT`) |
| 한도 초과 | **422** | 에러 본문 (`LIMIT_EXCEEDED`) |

**에러 본문 (모든 API 공통)**

```json
{ "code": "LIMIT_EXCEEDED", "message": "한도를 초과했습니다.", "paymentId": "P-1001" }
```

요청은 다음 순서로 검사합니다.

1. 입력 검증 (400)
2. 결제 ID 중복 (409)
3. 한도 (422)
4. 승인 (200)

### 5-2. 결제 취소

`POST /api/v1/payments/{paymentId}/cancel`

| 상황 | 상태 코드 | 본문 |
|---|---|---|
| 취소 성공 | **200** | `{"paymentId":"P-1001","status":"CANCELED","restoredAmount":50000,"remainingLimit":1000000}` |
| 없는 결제 | **404** | 에러 본문 (`PAYMENT_NOT_FOUND`) |
| 이미 취소됨 | **409** | 에러 본문 (`ALREADY_CANCELED`) |

### 5-3. 한도 조회

`GET /api/v1/users/{userId}/limit`

```json
{ "userId": "U-1", "dailyLimit": 1000000, "usedAmount": 50000, "remainingLimit": 950000 }
```

처음 조회하는 사용자는 `usedAmount`가 0입니다.

### 5-4. 수수료 계산

`GET /api/v1/fees?grade=GOLD&payType=DOMESTIC&amount=50000`

```json
{ "grade": "GOLD", "payType": "DOMESTIC", "amount": 50000, "fee": 250 }
```

- 입력이 잘못되면 400을 응답합니다.
- 같은 입력이라면 승인 API 응답의 `fee`와 같은 값이어야 합니다.

### 5-5. 한도와 결제 기록 규칙

| 규칙 | 내용 |
|---|---|
| 사용자당 한도 | 1,000,000원. 날짜별 초기화는 구현하지 않습니다. |
| 한도 차감액 | 결제 금액(`amount`). **수수료는 한도에 포함하지 않습니다.** |
| 승인 조건 | `사용액 + 이번 결제 금액 ≤ 1,000,000` |
| 취소 | 사용액에서 해당 결제 금액을 뺍니다. |
| 승인된 결제 | 기록이 계속 남습니다. 취소한 결제의 ID도 다시 사용할 수 없습니다. (409) |
| 거절된 결제 (422) | 기록하지 않습니다. 같은 ID로 다시 요청할 수 있습니다. |
| 항상 지켜야 할 조건 | `사용액 = 취소되지 않은 승인 결제 금액의 합`, `사용액 ≤ 1,000,000` |

## 6. 수수료 정책

수수료율을 bp 단위(1bp = 0.01%)로 다루면 정수로 계산할 수 있습니다. 예를 들어 1.00%는 100bp입니다.

| # | 규칙 |
|---|---|
| R1 | 금액이 **1,000원 미만**이면 수수료는 **0원**입니다. (면제) |
| R2 | 등급이 **VIP**이고 **국내** 결제이면 수수료는 **0원**입니다. (면제) |
| R3 | 기본 수수료율은 국내 **1.00%**, 해외 **3.00%**입니다. |
| R4 | **SILVER**는 기본 수수료율의 **80%**를 적용합니다. |
| R5 | **GOLD**는 기본 수수료율의 **50%**를 적용합니다. |
| R6 | **VIP** 해외 결제는 기본 수수료율과 관계없이 **1.50%**를 적용합니다. |
| R7 | **BASIC**은 기본 수수료율을 그대로 적용합니다. |
| R8 | 금액이 **1,000,000원 이상**이면 적용된 수수료율에서 **0.20%p**를 뺍니다. |
| R9 | 수수료는 `금액 × 수수료율`에서 **원 단위 미만을 버린** 값입니다. 면제가 아니면 **최소 100원**입니다. |
| R10 | 수수료는 **최대 50,000원**입니다. |

규칙은 다음 순서로 적용합니다.

1. 면제 확인 (R1, R2 순서)
2. 수수료율 결정 (R3~R7)
3. 고액 감면 (R8)
4. 원 단위 미만 버림과 최소 수수료 (R9)
5. 최대 수수료 (R10)

**계산 예시**

| 금액 | 등급 | 유형 | 수수료 | 설명 |
|---|---|---|---|---|
| 999 | BASIC | 국내 | 0 | 1,000원 미만이라 면제 (R1) |
| 1,000 | BASIC | 국내 | 100 | 계산 결과는 10원이지만 최소 수수료 100원 적용 |
| 12,350 | BASIC | 국내 | 123 | 123.5원에서 소수점 아래를 버림 |
| 999,999 | BASIC | 국내 | 9,999 | 고액 감면 대상이 아님 |
| 1,000,000 | BASIC | 국내 | 8,000 | 고액 감면 적용 (0.80%) |
| 5,000,000 | VIP | 국내 | 0 | 면제(R2)가 먼저 적용됨 |
| 10,000,000 | BASIC | 해외 | 50,000 | 계산 결과는 28만 원이지만 최대 수수료 적용 |

> [!WARNING]
> 시작 프로젝트에 들어 있는 기존 수수료 코드는 이 표와 다르게 동작하는 부분이 있습니다. 기존 코드가 아니라 이 표를 기준으로 구현해 주세요.

## 7. 문제 (6개)

1번부터 순서대로 푸는 것을 권장합니다. 6개 문제를 모두 풀어서 제출해 주세요.

### 문제 1. 결제 승인, 취소, 한도 조회 구현 (구현)

- 결제 컨트롤러의 `TODO`를 구현합니다. 5장의 규칙을 모두 지켜야 합니다.
- 요청이 동시에 들어와도 아래 조건이 지켜져야 합니다.
  - 같은 결제 ID는 1건만 승인되고, 나머지는 409를 응답합니다. 서로 다른 사용자가 같은 ID로 요청해도 마찬가지입니다.
  - 같은 사용자의 서로 다른 결제가 동시에 들어와도 한도를 넘지 않고, 사용액이 실제 승인 금액과 일치해야 합니다.
  - 같은 결제의 취소 요청이 동시에 여러 번 들어와도 한도는 한 번만 복원됩니다.
- 한도 저장소는 수정할 수 없고, 호출할 때마다 시간이 걸립니다. 동시성 처리는 저장소 바깥의 서비스 코드에서 해 주세요.

### 문제 2. 동시성 검증 테스트 작성 (테스트)

- 문제 1의 동시성 조건이 실제로 지켜지는지 확인하는 테스트를 작성합니다. 검증 방법은 자유입니다.
- 테스트를 작성할 때 다음을 참고해 주세요.
  - 스레드나 래치를 사용해 요청을 실제로 동시에 보냅니다.
  - 성공한 요청 수(예: 1건만 성공)와 최종 사용액을 함께 확인합니다.
  - 테스트 사이에 저장소를 초기화해서, 몇 번을 실행해도 같은 결과가 나오게 합니다.

### 문제 3. 수수료 정책 구현과 리팩토링 (구현)

- 6장의 규칙 표대로 수수료를 계산합니다. 기존 코드를 고쳐도 되고 새로 작성해도 됩니다.
- 계산 결과가 표와 같아야 하고, 코드를 읽었을 때 규칙이 잘 드러나야 합니다.
- 승인 API의 `fee`와 수수료 계산 API의 `fee`는 같은 값이어야 합니다.

### 문제 4. 수수료 정책 검증 테스트 작성 (테스트)

- 규칙이 바뀌는 경계값과 여러 규칙이 겹치는 경우를 확인하는 테스트를 작성합니다.
- 예: 999원과 1,000원, 999,999원과 1,000,000원, 최소 수수료와 최대 수수료, 등급별 차이

## 8. 시나리오 체크리스트

아래 시나리오는 모두 기대 결과대로 동작해야 합니다.

| # | 시나리오 | 기대 결과 |
|---|---|---|
| S1 | 정상 승인 | 200, 수수료와 잔여 한도가 맞음 |
| S2 | 같은 결제 ID로 다시 승인 요청 (순차) | 409 `DUPLICATE_PAYMENT`. 한도는 한 번만 차감됨 |
| S3 | 같은 사용자가 같은 결제 ID로 **동시에** 여러 번 요청 | **1건만 200**, 나머지 409. 사용액은 1건 금액만큼만 늘어남 |
| S4 | **서로 다른 사용자**가 같은 결제 ID로 동시에 요청 | **1건만 200** |
| S5 | 같은 사용자의 **서로 다른 결제**가 동시에 들어오고, 합계가 한도를 넘음 | 한도 안에서만 승인하고 나머지는 422. 사용액이 실제 승인 금액과 일치함 |
| S6 | 한도 경계 | 1,000,000원까지는 승인, 1원이라도 넘으면 422. 거절된 ID로 나중에 다시 요청 가능 |
| S7 | 입력 오류 | 승인 API와 수수료 API 모두 400 |
| S8 | 승인된 결제 취소, 없는 결제 취소 | 승인된 결제는 200과 한도 복원, 없는 결제는 404 |
| S9 | **같은 결제의 취소** 요청이 동시에 여러 건 | **1건만 200**, 나머지 409. 한도는 한 번만 복원됨 |
| S10 | 취소한 결제 ID로 다시 승인 요청 | 409. 한도는 바뀌지 않음 |
| S11 | **승인과 취소가 섞여** 동시에 들어옴 | 처리 순서와 관계없이 최종 사용액이 취소되지 않은 승인 결제 금액의 합과 같음 |
| S12 | 수수료 규칙 (경계값 포함) | 모든 입력에서 표와 같은 수수료 |

S5 예시: 한도가 1,000,000원인 사용자에게 400,000원 결제 3건이 서로 다른 ID로 동시에 들어오면 2건은 승인, 1건은 거절되고 사용액은 800,000원이어야 합니다.

## 10. 제출 방법

- `starter-project/` 폴더를 제출 저장소의 루트로 사용합니다. 아래에서 말하는 루트는 이 폴더입니다.
- 시작 프로젝트에서 이어서 작업하고, 루트에 `README.md`와 `docs/answer.md`를 둡니다.
- 루트에서 `./gradlew bootRun`으로 실행되어야 하며, 포트는 8080입니다.
- 루트에서 `./gradlew test`를 실행했을 때 모든 테스트가 통과해야 합니다.
- 한도 저장소, 결제 기록 클래스, API 경로와 형식, 설정 파일은 바꾸지 않습니다.
- `README.md`에는 실행 방법과 직접 확인한 시나리오를 적어 주세요.
